# React Migration Recovery Plan

## Scope

This plan covers the migration of the public renter-facing experience from the
legacy HTML/CSS/JavaScript pages to the React/Tailwind frontend while preserving
the existing Supabase, Cloudflare Pages, Edge Function, authentication, storage,
and application contracts.

The admin, landlord, tenant, lease-signing, and other protected workflows should
remain on their legacy pages until an equivalent replacement is implemented and
verified. They are not safe to remove as part of the public-site migration.

## Scan summary

The repository is currently in a hybrid, incomplete migration state:

- The root build runs a Vite build from `frontend/`, copies the result into
  `dist/index.html`, and then overwrites a list of public `.html` files with the
  React entry point.
- The project guide still describes `frontend/` as an experimental shell and
  the legacy site as the production entry point, which conflicts with the build
  script and redirect rules.
- The React frontend has a new dark slate/cyan visual system. The legacy
  public site uses the existing Choice Properties design system, theme handling,
  richer page layouts, and established interaction behavior. The current React
  pages are not visual or functional parity replacements.
- No Replit workflow is configured. This is not itself a production defect
  because production is Cloudflare Pages, but it prevents a reliable local
  browser verification loop.

## Confirmed blockers and high-risk defects

### P0 — The current frontend build cannot complete in the imported environment

Observed:

- `.replit` requests Node 18.
- The migrated packages resolve to versions requiring Node 20 or newer,
  including Tailwind Oxide, Oxlint, and React Router.
- `npm run build` reaches the TypeScript phase but fails while loading the
  Tailwind Vite plugin because its native binding is missing.
- `npm run lint` fails for the same optional-native-binding problem.
- Both commands emit `EBADENGINE` warnings under Node 18.

Impact: there is no trustworthy `dist/` output to preview or deploy, so browser
testing of the migration cannot begin.

Recovery:

1. Align the local/imported runtime with the Cloudflare build runtime (Node 20
   or newer).
2. Decide and document one lockfile/install policy for the root project and
   `frontend/`; do not rely on a nested build-time `npm install` to silently
   change dependency resolution.
3. Reinstall optional platform packages under the supported runtime and verify
   that Vite and Oxlint load their native bindings.
4. Keep the project’s existing Vite/Tailwind/React stack; do not migrate the
   repository to a different workspace or package manager as part of this
   recovery.
5. Make `npm run build` and `npm run lint` pass before any UI parity work is
   accepted.

### P0 — Application links target a route whose build output is deleted

Observed:

- React property and card CTAs generate `/apply/?...`.
- The legacy redirect maps `/apply/*` to `/apply/index.html`.
- `scripts/merge-react.js` removes `dist/apply/` after copying the legacy site.
- The React router has `/apply` and `/apply.html`, but not `/apply/`.
- The React application also constructs a fallback URL containing
  `/apply/index.html`.

Impact: the most important conversion path can resolve to a file that no longer
exists, depending on the Cloudflare rewrite path. The same mismatch affects
resume links generated by the existing save-draft service.

Recovery:

1. Choose one canonical public application URL, preferably `/apply/`, and make
   the built output and Cloudflare rewrite point to a real React entry.
2. Update all React CTAs, server-generated resume links, redirects, and
   fallback links to use that canonical route.
3. Preserve compatibility aliases for old links such as
   `/apply/index.html`, `/apply.html`, and historical dashboard URLs.
4. Do not delete the legacy application directory until every legacy link,
   resume link, email link, and protected flow has been mapped and tested.

### P0 — React application submission reports success when submission fails

Observed in `frontend/src/pages/ApplyPage.tsx`:

- A client-generated ID is created with `Date.now()` and `Math.random()`.
- The request error is caught and only logged.
- The page then unconditionally renders the generated ID as a successful
  submission.
- The server-generated `appId` and `portal_login_url` are not used.

Impact: applicants can be told that an application was accepted when the Edge
Function rejected it, timed out, or was unreachable. The displayed ID may not
exist in the database.

Recovery:

1. Treat only a successful, validated Edge Function response as success.
2. Display the server-returned application ID and portal URL.
3. Keep a clear retryable error state for network, validation, rate-limit, and
   server errors.
4. Add duplicate-submit protection and preserve the server’s idempotency
   behavior.
5. Never use a locally generated identifier as proof of persistence.

### P0 — The React form does not preserve the legacy application contract

The legacy form and `receive-application` Edge Function support substantially
more fields than the React model, including co-applicant details and consent,
supervisor information, second references, emergency relationship, payment
preferences, preferred contact details, vehicle details, and other disclosures.

The React request also does not preserve the legacy submission safeguards and
metadata path, including the client CSRF nonce field and the complete field-name
contract expected by the Edge Function.

Impact: submissions can be incomplete, screening/admin records can lose
information, and server-side bot/idempotency protections can be bypassed or
malfunction.

Recovery:

1. Treat the legacy HTML `name` attributes and the Edge Function mapping as the
   canonical contract.
2. Build a typed React form model that covers every persisted field required by
   the existing application flow.
3. Preserve exact field names and boolean/number encodings expected by
   `receive-application`.
4. Reimplement CSRF nonce generation, submission UUID/idempotency handling,
   attachment encoding/size behavior, duplicate submission handling, and
   server response handling.
5. Preserve application drafts, resume links, progress recovery, and the
   existing consent/disclosure copy.
6. Add contract tests using representative valid, invalid, duplicate, and
   attachment-bearing payloads before switching the canonical route.

## Functional parity gaps

### Public listings

The legacy listings flow uses `CP.Properties.getListings()` with server-side
filtering, sorting, pagination, URL state, and additional filters. The React
adapter currently performs a direct `properties` table query with a fixed
limit, then filters only the rows already loaded in the browser.

The recovery must restore:

- Server-side search and filtering rather than filtering only the first batch.
- URL-synchronized query state and shareable filtered links.
- Current sort options and pagination.
- Minimum beds/baths, rent range, property type, pets, parking, laundry,
  heating, availability, and other filters supported by the legacy API.
- Loading skeletons, empty results, retry states, and actionable backend errors.
- Map view and location behavior where supported by the existing site.
- Saved-property behavior for anonymous and authenticated visitors.
- Full property-card data, image transformations, badges, and availability
  rules.

### Property detail

The legacy detail page includes richer property fields, ordered galleries,
lightbox behavior, ImageKit transforms, map/location behavior, landlord data,
inquiry/contact behavior, similar listings, application context, structured
metadata, and availability guards. The React detail adapter currently selects
only a small subset of those fields and the component implements only a subset
of the interactions.

The recovery must:

- Use `property_photos` as the source of truth and preserve ordering, hero
  selection, transforms, and fallback images.
- Restore all public-safe property facts and enrichment sections.
- Restore landlord card and verified contact behavior without exposing private
  fields.
- Restore map fallback and map-opening behavior, including graceful operation
  when Geoapify is not configured.
- Restore inquiry/contact drawer behavior and validation.
- Restore similar-listing recommendations.
- Preserve the rule that smoking information is not shown on property pages.
- Keep application fee, pet, and deposit values server-authoritative and
  consistent with current project rules.

### Navigation, theme, and shared shell

The old shell includes the Choice Properties navigation drawer, active route
state, theme persistence/toggle behavior, dynamic contact values, responsive
mobile behavior, shared footer, and legacy compatibility links. The React shell
has a separate dark-only visual system and does not yet demonstrate parity with
those behaviors.

The recovery must:

- Extract the existing design tokens from `css/cp-design.css` into Tailwind
  theme variables/utilities rather than inventing a second brand system.
- Match the old light/default appearance and preserve the supported dark theme.
- Preserve mobile drawer keyboard/focus behavior and route highlighting.
- Use one shared React shell across public pages.
- Keep absolute links to protected legacy portals where those portals remain the
  source of truth.
- Eliminate dead links, accidental full-page navigations, and inconsistent
  `.html`/extensionless URL variants.

### Informational and legal pages

React versions exist for several informational pages, but the migration does
not cover every root public page and the current React index metadata is shared
across routes. The plan must explicitly classify each page as migrated,
legacy-compatible, or intentionally protected.

For every public page that is moved to React:

- Preserve the complete approved content and policy wording.
- Preserve internal links and anchors.
- Add route-specific title, description, canonical, Open Graph, Twitter, and
  structured metadata where applicable.
- Preserve accessible headings, landmarks, keyboard behavior, and responsive
  layout.
- Keep the existing policy and legal source content authoritative during the
  visual conversion.

Pages such as `about.html`, `application-credit-policy.html`, `matches.html`,
and operational utility pages must not be silently swallowed by the SPA
catch-all. Each needs an explicit route decision.

### Shared runtime compatibility

The legacy public pages explicitly load combinations of `config.js`,
Supabase, `cp-ui.js`, `cp-api.js`, `components.js`, and page-specific scripts.
The React entry loads a smaller set and uses a bridge around global `CONFIG`,
`supabase`, and `CP`.

Before relying on the bridge, verify:

- Script order and readiness under normal, slow, and cached browser loads.
- Whether all `CP.UI` helpers used by React are available without
  `cp-ui.js`.
- Session persistence and auth refresh behavior across public-to-portal
  navigation.
- CSP nonces and Cloudflare middleware behavior for the Vite-generated entry.
- ImageKit/config behavior when optional build variables are absent.
- That the SPA fallback does not intercept admin, landlord, tenant, extension,
  function, or blocked documentation paths.

## Ordered implementation phases

### Phase 1 — Establish a reproducible baseline

- Align Node and dependency installation with the supported build runtime.
- Produce a clean Vite build, lint result, and generated `dist/`.
- Record the exact build output inventory.
- Add a minimal local preview workflow only if needed for browser verification;
  production remains Cloudflare Pages.

**Exit criteria:** build and lint pass from a clean install, and the generated
output can be served without missing asset errors.

### Phase 2 — Make routing and deployment handoff safe

- Define the public React route matrix and legacy protected route matrix.
- Fix the `/apply/` entry mismatch before exposing React CTAs.
- Make every redirect target exist in `dist/`.
- Preserve legacy aliases and deep links.
- Replace the broad SPA catch-all with explicit handling for known public pages
  and a real not-found page where appropriate.
- Verify `_redirects`, `_headers`, middleware CSP, asset paths, and generated
  config together.

**Exit criteria:** every public route, legacy alias, application link, and
protected portal link returns the intended document in a built preview.

### Phase 3 — Restore shared data and auth contracts

- Implement a typed adapter around the existing public listing/detail API
  contract, preferably reusing the established `CP.Properties` behavior rather
  than duplicating query semantics.
- Expand property types and mappings to cover the fields used by the legacy
  cards/detail page.
- Add a shared auth/session provider with auth-state subscription and clear
  loading/error states.
- Reconcile anonymous saved properties with authenticated saved properties
  without losing local saves.
- Treat Supabase errors as user-visible state, not silent empty results.

**Exit criteria:** listings and details show the same records, ordering,
availability rules, photos, and public-safe fields as the legacy flow for the
same query.

### Phase 4 — Rebuild public UI parity on the new component architecture

- Convert legacy design tokens and responsive breakpoints into Tailwind
  variables/utilities.
- Rebuild the shared nav/footer/theme shell.
- Rebuild listings search, filters, sort, pagination, map, cards, and saved
  states.
- Rebuild property detail gallery, lightbox, facts, map, landlord, inquiry,
  similar listings, and application CTAs.
- Rebuild informational/legal page layouts from their approved source content.
- Add responsive behavior for narrow mobile, tablet, and desktop widths.

**Exit criteria:** visual comparison at representative viewports shows the
  React pages preserve the old information hierarchy, content, controls,
  states, and responsive behavior while using the new component implementation.

### Phase 5 — Port the application flow without weakening it

- Port the complete legacy form model and all required/conditional sections.
- Preserve exact backend field names and consent semantics.
- Port validation, progress state, auto-save/draft/resume, file handling,
  duplicate protection, CSRF, idempotency, and server response behavior.
- Return server-generated IDs and portal URLs only.
- Test failure states deliberately; never render success after a rejected
  request.
- Keep the old application entry available as a rollback path until the React
  flow has passed production-like tests.

**Exit criteria:** valid submissions create exactly one correct application;
invalid submissions do not create records; failed requests show retryable
errors; duplicates are handled by the existing server contract; documents and
consents are preserved.

### Phase 6 — SEO, accessibility, and production hardening

- Add route-aware metadata and structured data.
- Verify keyboard navigation, focus management, labels, error announcements,
  dialogs, menus, and reduced-motion behavior.
- Verify image loading, ImageKit transforms, lazy loading, alt text, and
  fallback behavior.
- Confirm CSP, CORS, Supabase RLS expectations, and public/private data
  boundaries.
- Verify caching does not retain generated config or stale HTML.

**Exit criteria:** no console errors on the supported public flows, no
accessibility-critical regressions, and no private data leaks in the browser.

### Phase 7 — Cutover and rollback readiness

- Run the full browser regression matrix against a built preview.
- Compare React and legacy behavior on the same property IDs and application
  scenarios.
- Enable React routes for one public surface at a time.
- Monitor error reporting and Edge Function responses after each cutover.
- Retain a documented rollback switch until the new routes are stable.
- Update the project guide so it no longer contradicts the chosen production
  entry point.

**Exit criteria:** all in-scope public routes use the React design, protected
legacy routes still work, the application flow is trustworthy, and rollback is
documented and tested.

## Verification matrix

The final implementation should be checked at minimum with:

1. Clean install under the supported Node version.
2. `npm run build`.
3. `npm run lint`.
4. Built preview on mobile and desktop widths.
5. Home/listings load, retry, empty, search, filters, sort, pagination, map,
   and saved states.
6. Property detail with valid, missing, unavailable, and malformed IDs;
   gallery/lightbox, map fallback, inquiry, saved, and application links.
7. Application route aliases, prefilled property context, every form step,
   validation, draft/resume, attachments, invalid submission, network failure,
   successful submission, and duplicate submission.
8. Public-to-tenant and public-to-landlord navigation.
9. Admin, landlord, tenant, auth callback, extension, and blocked-path
   regression checks to ensure the SPA does not capture protected routes.
10. Cloudflare Pages preview with generated config and CSP middleware enabled.

## Explicit non-goals

- Do not migrate the repository to a new framework or database.
- Do not replace Supabase or the existing Edge Functions.
- Do not remove admin, landlord, tenant, lease, scraper, or extension flows
  merely because the public shell moved to React.
- Do not relax application validation, consent, CSRF, idempotency, or
  server-authoritative pricing rules to make the React form easier to port.
- Do not mark the migration complete based only on a successful TypeScript
  compile; functional and browser verification are required.
